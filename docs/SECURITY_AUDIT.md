# 本地数据与安全审计

审计对象：`MindCard/app` 当前版本（含图片题、短期/长期卡组）。  
目标：判断是否存在本地数据泄露，以及新用户使用时的安全隐患。

---

## 结论摘要

1. **应用本身没有发现主动上传数据的行为**：没有 `fetch`、`XMLHttpRequest`、`sendBeacon`、第三方脚本、统计或字体 CDN。
2. **但本地数据不是加密的**：卡组、答案、图片、学习记录都以明文存在 `localStorage`，同源页面、浏览器扩展、共用电脑的其他使用者都能读取。
3. **最大的结构性风险是 GitHub Pages 同源共享**：部署在 `https://<user>.github.io/MindCard/` 时，同一个用户名下的其他项目页面也属于 `https://<user>.github.io`，可以读取全部 `mindcard:*` 数据。
4. **导出文件、回收站、备份和损坏副本会保留数据**：用户以为“删掉了”，实际可能还在。
5. **导入不受信任的卡组不会直接执行代码**（当前渲染都做了转义），但可以造成卡顿、占满存储、原型链污染或图片解压炸弹。
6. **“长期卡组只读”和“短期上限”是客户端 UX，不是安全边界**：开发者工具或同源脚本可以直接改。

## 1. 数据流

### 数据存在哪里

| 数据 | 位置 | 是否明文 |
| --- | --- | --- |
| 卡组内容（含答案、图片 Data URL） | `mindcard:deck:<id>` | 是 |
| 学习进度、日志、隐藏卡片 | `mindcard:progress:<id>` | 是 |
| 上一版本进度 | `mindcard:progress:<id>:bak` | 是 |
| 卡组回收站 | `mindcard:deck-trash` | 是 |
| 损坏现场 | `mindcard:corrupt:<time>` | 是 |
| 全局设置 | `mindcard:settings` | 是 |
| 导出的卡组/进度/全部备份 | 用户下载目录 | 是 |

### 有没有网络上传

- 没有后端 API；
- 没有第三方脚本、统计、字体、CDN；
- 图片是 Data URL，不会请求外部图床；
- GitHub Pages 只负责提供静态文件，不会收到卡组内容。

**所以：应用不会主动把卡组传到服务器。风险在“本地可被谁读”和“用户把文件放到了哪里”。**

## 2. 本地数据泄露风险

| 风险 | 严重度 | 说明 |
| --- | --- | --- |
| **GitHub Pages 同源共享** | **高** | 同一用户名下的所有项目页面共享 `https://<user>.github.io` origin；同源的任何 JS 都能读 `localStorage` |
| **共用电脑/浏览器 profile** | **高** | 下一个使用者打开 DevTools 或同浏览器即可看到全部卡组、答案、图片和记录 |
| **浏览器扩展** | 中高 | 有“读取和更改所有网站数据”权限的扩展可以读 localStorage |
| **导出文件/云同步** | 中高 | JSON 是明文；下载目录若同步到 OneDrive/iCloud/网盘，等于上传 |
| **回收站/备份/损坏副本** | 中 | 删除卡组、卡片后仍可能保留；`:bak` 和 `corrupt:*` 没有清理入口 |
| **图片内容/EXIF** | 中 | 上传图片会重新编码，通常去掉 EXIF；但图片本身可能含证件、成绩、人脸等敏感信息 |
| **`file://` 直接打开** | 中 | 部分浏览器会把所有本地 HTML 视为同一来源；其他本地页面可能读到数据，行为因浏览器而异 |
| **XSS / CSP** | 低（当前） | 未发现直接 XSS；所有文本转义，图片限制为 data:image；但没有 CSP 兜底 |
| **供应链/部署** | 低中 | GitHub Actions 使用 tag 而非 SHA；仓库或账号被攻破后，恶意 JS 可读同源 localStorage |
| **点击劫持** | 低 | 没有 `frame-ancestors`；GitHub Pages 不能自定义响应头 |

### 2.1 同源共享为什么危险

`localStorage` 按 **origin** 隔离，不按路径隔离。

如果地址是：

```
https://alice.github.io/MindCard/
```

那么以下页面都属于同一个 origin：

```
https://alice.github.io/other-project/
https://alice.github.io/another-app/
```

这些页面里的任意 JavaScript 都可以：

```js
localStorage.getItem('mindcard:deck:my-course')
localStorage.getItem('mindcard:progress:my-course')
```

也就是说，**同一 GitHub 用户名下的任何一个 Pages 项目、或其中被注入的脚本，都能读取 MindCard 的数据**。

如果使用独立域名：

```
https://mindcard.example.com/
```

则只有这个域名下的页面能读，风险小得多。

### 2.2 `file://` 的情况

直接双击 `app/index.html` 时，`file://` 的存储隔离规则由浏览器决定，规范没有保证。  
部分浏览器会把所有本地 HTML 视为同一来源，其他本地页面可能读到 `mindcard:*`。  
**不要把 `file://` 当作安全边界；敏感数据建议用 localhost 或独立域名。**

### 2.3 删除不等于抹除

- 删除卡组 → 进 `mindcard:deck-trash`，进度还在；
- 删除卡片 → 进 `S.hidden`，内容还在卡组里；
- 每次保存 → 可能留 `:bak`；
- 数据损坏 → 可能留 `mindcard:corrupt:*`；
- “导出全部” → 默认包含回收站和删除内容。

如果用户把备份发给别人，可能把已经“删掉”的内容一起发出去。

## 3. 新用户使用时的安全隐患

### 场景 A：在共用电脑上使用

- 卡组、答案、图片、学习记录都留在浏览器 profile 里；
- 下一个使用者打开同一浏览器即可看到；
- 隐私模式只能减少残留，不能防止使用期间的旁观/扩展读取。

**建议**：共用电脑不要导入敏感卡组；用完彻底删除卡组并清理浏览器站点数据。

### 场景 B：直接打开公开示例

- 公开站点只含示例卡组，没有课程内容；
- 新用户导入自己的卡组后，数据只存在本机，不会上传；
- 但如果部署在共享的 `*.github.io` origin，其他同源项目可读。

### 场景 C：导入陌生人分享的卡组

当前防护：

- HTML 会转义，不会直接执行 `<script>`；
- 图片只允许 `data:image/(png|jpeg|webp|gif)`，SVG 被拒绝；
- 卡片/章节结构会校验。

但仍有风险：

1. **超大数据**：20 MB JSON 可以包含大量卡片/长文本，渲染时卡死；
2. **图片解压炸弹**：小体积 PNG 可以有超大尺寸，浏览器解码占用大量内存；
3. **占满存储**：大量 Data URL 图片迅速逼近 5 MB，导致保存失败；
4. **原型链边界**：卡片 id 允许 `__proto__` 这类名字，可能污染普通对象映射，造成进度错乱或页面异常；
5. **内容欺骗**：卡片可以伪装成“登录页/通知/客服”，虽然不能执行代码，但可能骗用户输入信息或扫码。

**建议**：只导入信任来源的卡组；导入前看预览；不要导入来源不明的“全部备份”。

### 场景 D：使用“导入全部备份”

- 会覆盖同 id 卡组和进度；
- 只弹一次确认；
- 恶意备份可以清空/覆盖现有数据，或塞入大量图片。

**建议**：导入前先导出自己的备份；把“全部备份”当作高风险操作。

### 场景 E：以为长期卡组受保护

“长期卡组只读”只是前端标志：

- DevTools 可以改 `localStorage`；
- 同源脚本可以改；
- 短期数量上限也可以绕过。

**它不是权限系统，不能防止有意修改。** 只能防止误操作。

### 场景 F：导出/分享

- 导出的 JSON 含题目、答案、图片，可能还有进度和日志；
- “导出全部”还包含回收站；
- 文件放进网盘、Git 仓库、聊天工具后，就离开了本机保护范围。

**建议**：分享前用“导出卡组”而不是“导出全部”；不要把 `../MindCard-private/` 或备份提交到公开仓库。

### 场景 G：使用修改版/ fork

- 任何能修改 `app.js` 的人都可以加入读取 localStorage 并上传的代码；
- 静态站点没有签名/完整性校验；
- 如果修改版和原版同源，它能读原版留下的数据。

**建议**：只用可信来源的构建；敏感数据不要在同一 origin 上试用来路不明的 fork。

## 4. 当前做得好的地方

- 没有第三方脚本、统计、外部字体、图床请求；
- 文本渲染统一 `esc()`，Markdown 先转义再替换，没有发现 raw HTML 注入；
- 图片 `src` 限制为 `data:image/(png|jpeg|webp|gif)`，拒绝 SVG；
- 卡组/章节/卡片 id 有格式校验；
- 部署 workflow 只上传 `app/`，公开仓库只含示例卡组；
- 课程卡组放在仓库外的 `../MindCard-private/`，不进公开仓库/Pages；
- 长期卡组在 UI 层确实禁用了编辑和删卡入口；
- 保存失败有横幅提示，不会静默丢数据。

但这些都是**功能/误操作防护**，不是**对抗本机攻击者**的安全边界。

## 5. 具体弱点与证据

### 5.1 明文 localStorage

- 卡组：`mindcard:deck:<id>`
- 进度：`mindcard:progress:<id>`
- 备份、回收站、损坏副本同样是明文 JSON。

任何同源脚本、扩展、DevTools 都能直接读。

### 5.2 没有加密

- 没有 WebCrypto 加密；
- 没有密码/PIN；
- 依赖操作系统账户和磁盘加密。

### 5.3 同源页面

- `https://<user>.github.io/*` 共享 origin；
- 若用自定义域名，同一域名下的其他应用仍共享。

### 5.4 导入缺少上限

- 文件大小限制 20 MB；
- 但没有限制卡片数量、标题长度、题目/答案长度、图片总大小；
- 渲染是同步全量，极端卡组会卡死页面。

### 5.5 卡片 id 允许 `__proto__`

校验正则允许下划线开头，`__proto__` 可以通过。  
`byId`、`S.cards` 等是普通对象，赋值 `obj['__proto__'] = ...` 会改原型，可能造成：

- 进度读不到；
- 卡片查找异常；
- 统计/渲染报错。

不是远程代码执行，但属于不受信任输入导致的数据完整性问题。

### 5.6 图片

- 上传图片经过 canvas 重编码，通常会去掉 EXIF；
- 但**导入的卡组图片不会重新编码**，原始 Data URL 中的元数据可能保留；
- 图片本身可能含证件、成绩、人脸、二维码等敏感信息；
- 导入图片没有尺寸/总大小限制，存在解压炸弹风险。

### 5.7 没有 CSP

`index.html` 没有 `Content-Security-Policy`。  
当前没有发现 XSS，但一旦未来某处漏转义，CSP 不能作为第二道防线。  
GitHub Pages 不能自定义响应头，只能用 `<meta http-equiv="Content-Security-Policy">` 做部分限制。

### 5.8 仓库外私有目录不是保险箱

- 课程卡组现在放在仓库外的 `../MindCard-private/`，不会进 Git；
- 但不阻止本地其他用户、云备份、压缩包、误复制；
- 不要把它复制回仓库；如果必须放回，至少加 pre-commit 拦截。

### 5.9 部署供应链

`pages.yml` 使用 `actions/checkout@v4` 等 tag，不是 commit SHA。  
仓库/账号/Action 被攻破时，恶意 JS 可以在同源读取全部数据。

## 6. 建议

### P0：优先处理

1. **换独立 origin**
   - 用自定义子域名部署，例如 `mindcard.example.com`；
   - 或只在 localhost 使用；
   - 避免 `https://<user>.github.io/MindCard/` 与其他项目共享 origin。

2. **首次使用隐私提示**
   - 明确写：数据仅在本浏览器、未加密、共用电脑/扩展/同源页面可读；
   - 不要使用“绝对私密”“只有你能看到”这类表述。

3. **导入上限与 ID 加固**
   - 限制卡片数（如 5000）、标题/题目/答案长度、图片总大小；
   - 禁止 `__proto__`、`constructor`、`prototype` 作为卡片 id；
   - 用 `Object.create(null)` 或 `Map` 存 `byId`/状态映射；
   - 导入图片重新编码并限制尺寸。

4. **可彻底删除**
   - 提供“清空回收站”“清理备份/损坏副本”；
   - “导出全部”明确标注包含已删除内容，或默认排除回收站。

### P1：建议处理

5. **可选加密**
   - WebCrypto AES-GCM + 口令派生（PBKDF2/Argon2）；
   - 解锁期间仍可能被 XSS 读取，但能保护静态文件和云备份。

6. **CSP**
   - `default-src 'self'; script-src 'self'; img-src 'self' data:; connect-src 'none'; object-src 'none'; base-uri 'none'`；
   - 因为大量内联 style，先加 `style-src 'self' 'unsafe-inline'`，后续再收紧。

7. **安全导出**
   - 分享用“导出卡组”，不要用“导出全部”；
   - 导出前提示文件包含答案/图片/进度。

8. **明确只读不是安全**
   - 文档和 UI 都说明：长期只读只防误操作，不防有意修改。

### P2：长期

9. 桌面 App + 系统密钥链/磁盘加密；
10. 发布构建签名/校验和；
11. 如果做云端，必须加账号、传输加密、访问控制和隐私政策。

---

## 7. 安全使用清单

- [ ] 不用共用电脑保存敏感卡组；
- [ ] 不使用来源不明的卡组/备份；
- [ ] 分享前只导出需要的卡组，不用“导出全部”；
- [ ] 定期导出备份，但把备份当成敏感文件保管；
- [ ] 删除敏感卡组后，清空回收站并清理浏览器站点数据；
- [ ] 敏感内容配合操作系统磁盘加密；
- [ ] 用独立域名/localhost，避免共享 origin；
- [ ] 不把仓库外私有目录、导出的 JSON、含图片的备份提交到公开仓库。

---

## 8. 一句话总结

**没有发现应用主动外传数据；真正的风险是“同源可读 + 明文存储 + 共用设备 + 导出/残留 + 不受信任导入”。**  
如果内容确实敏感，优先换独立 origin、加导入上限和彻底删除；需要更强保护时再做可选加密或桌面端。
